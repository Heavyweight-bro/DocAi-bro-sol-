# Впровадження в компанії

Документ лише для розробника та адміністратора. Цей матеріал не показується в інтерфейсі користувача.

Що вже працює, що потрібно додати та як взаємодіють частини системи.

Поточна версія: один робочий простір, вибір AI-провайдера та послідовна обробка в браузері. Облікові записи, розмежування доступу й серверна черга ще не реалізовані.

## Окремий застосунок для однієї компанії

Та сама програма, але власна адреса (наприклад, docs.company.ua), база даних, сховище файлів та ключі AI. У налаштуваннях уже можна змінити назву компанії. Це змінює вивіску, а не створює ізоляцію даних.

Для повноцінного запуску адміністратор розгортає сервер, підключає БД і HTTPS, а розробник додає вхід співробітників та права доступу. Ключі провайдерів залишаються на сервері.

## Коли користувачів багато

| Одна компанія | Сервіс для кількох компаній |
|---|---|
| Запрошення співробітників і ролі: адміністратор, оператор, перегляд. | Додатково: окремий простір організації та членство користувача. |
| Права на документи й шаблони перевіряє сервер. | Усі записи, файли, завдання й API-ключі прив’язані до organization_id. |
| Журнал дій, резервні копії, ліміти обробки. | Ізоляція через політики БД, квоти та перевірки доступу для кожної компанії. |

Самого поля «компанія» недостатньо: користувач не має отримувати чужі дані навіть прямим API-запитом.

## База даних — реєстр роботи

Зберігає користувачів, шаблони, статуси та витягнуті дані. Самі PDF і скани краще тримати в окремому файловому сховищі, а в БД — посилання на них.

Практичний варіант: керований PostgreSQL, наприклад Supabase. Адміністратор створює проєкт і регіон, застосовує схему таблиць та права, вмикає резервні копії й передає серверу реквізити підключення. Локальний JSON-файл у поточній версії — лише для роботи на одному комп’ютері.

## Черга — диспетчер завдань

Зараз файли йдуть один за одним, поки відкрита сторінка. Серверна черга дозволить закрити браузер: сервер збереже завдання, а окремий процес-виконавець (worker) обробить його незалежно від користувача.

1. Файл зберігається у сховищі, завдання отримує ID і статус «Очікує».
2. Worker бере завдання, читає шаблон і надсилає документ обраному AI.
3. Результат записується в БД, статус змінюється на «Готово» або «Помилка».
4. Тимчасові помилки повторюються з паузою; невірний ключ потребує виправлення.

Для реалізації: Redis + BullMQ і worker, або черга на PostgreSQL. Також потрібні захист від повторної обробки, обмеження паралельних запитів і моніторинг. Підключення Redis саме по собі не додає чергу — її логіку треба реалізувати.

## Як працює API шаблону

API — це «вхідні двері» для іншої програми. Ви створюєте шаблон «Рахунок» з ідентифікатором invoice. Адреса `POST /api/parse/invoice` приймає файл і застосовує саме цей шаблон. Нова копія сервера не створюється.

CRM надсилає файл → сервер знаходить шаблон → AI витягує поля → сервер зберігає результат → CRM отримує JSON з ID документа. Сто рахунків використовують одну адресу, але мають сто різних ID. Збережений результат доступний через `GET /api/documents/:id` без повторного виклику AI.

Зараз відповідь приходить після завершення обробки. Після додавання серверної черги планується відповідь `202 + jobId`; результат можна буде отримати запитом статусу або webhook. Ці асинхронні адреси поки не реалізовані.
