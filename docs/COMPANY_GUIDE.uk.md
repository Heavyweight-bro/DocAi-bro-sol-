# Doc.AI для компанії: пояснення без технічного жаргону

## Що вже є

Завантаження файлів, шаблони з інструкціями, три незалежні AI-провайдери, збереження результатів, JSON-експорт, історія, API шаблонів і отримання результату за ID. У налаштуваннях можна змінити назву компанії та підключити OpenAI, Gemini або Anthropic. Зміна назви не створює окремої бази чи окремої компанії.

**Чого ще немає:** входу співробітників, ролей, ізоляції компаній, серверної черги та гарантованої перевірки правильності витягнутих даних. Не слід вважати цю локальну версію готовим багатокористувацьким сервісом.

## 1. Зробити окремо для однієї компанії

Уяви окремий офіс: власна адреса, архів, список співробітників і рахунок за AI. Код програми може бути тим самим, але розгортання та дані — окремі.

Потрібно:

1. Адреса, наприклад docs.company.ua, та HTTPS.
2. Сервер для застосунку. На етапі серверної черги — також окремий процес worker.
3. PostgreSQL для даних; простий керований варіант — Supabase.
4. Приватне файлове сховище для оригіналів PDF/сканів.
5. API-ключ обраного AI-провайдера з доступом до потрібної моделі.
6. Вхід співробітників, ролі та журнал дій. Це потрібно додати в код.
7. Резервні копії, перевірка відновлення й відповідальний адміністратор.

Тобі потрібно визначити, хто працює з системою, які документи вона обробляє, хто бачить результат і скільки часу зберігаються файли. Адміністратор налаштовує інфраструктуру; розробник додає права, чергу та інтеграції.

## 2. Зробити багатокористувацьким

Для співробітників однієї компанії потрібні персональні облікові записи і ролі. Наприклад: адміністратор налаштовує підключення, оператор завантажує й перевіряє, користувач із правом перегляду читає дозволені результати.

Для кількох компаній додатково потрібне членство в організації та organization_id у шаблонах, документах, завданнях і API-ключах. Сервер отримує компанію з перевіреної сесії користувача, а не довіряє значенню, яке користувач написав у запиті. Файли й рядки БД мають бути ізольовані. Перевірка доступу обов’язкова також у worker та інтеграціях.

У Supabase для цього використовують політики Row Level Security. Сервісний ключ може обходити RLS: він залишається на сервері, а сервер окремо перевіряє права. Самого приховування кнопок в інтерфейсі недостатньо.

## 3. БД: що купити, налаштувати та зберігати

**БД — реєстр**, де записано: хто завантажив файл, який шаблон застосовано, чи завершена обробка та які поля отримано. **Файлове сховище — архів**, де лежать оригінали документів. **AI — виконавець**, який читає файл.

Для керованого PostgreSQL адміністратор створює проєкт, обирає погоджений регіон, застосовує схему таблиць, налаштовує права, резервні копії та передає серверу реквізити підключення. Не потрібно вручну встановлювати PostgreSQL на ноутбук.

Для поточної програми основні таблиці — document_types і documents. Для корпоративної версії додаються організації, користувачі/членство, завдання та журнал дій. Шаблон і модель варто фіксувати в завданні: зміна шаблону завтра не повинна змінювати зміст учорашньої обробки.

Резервна копія БД не замінює резервної копії файлів. Потрібні обидві та перевірений сценарій відновлення. Зараз без Supabase історія зберігається локальним JSON-файлом, а оригінали не зберігаються після запиту.

## 4. Черга: чому одного сервера недостатньо

Зараз чергою керує відкрита вкладка браузера. Якщо її закрити, наступні файли не почнуть оброблятися. Серверна черга — постійний список завдань, незалежний від вкладки.

Майбутня робота:

1. Сервер приймає файл, зберігає його та видає номер завдання.
2. Worker бере завдання з черги і змінює статус на «Обробка».
3. Викликає AI, перевіряє JSON, записує результат у БД.
4. Позначає «Готово», або зберігає зрозумілу помилку.
5. Інтерфейс показує результат, навіть якщо його відкрили пізніше.

Один варіант реалізації — Redis + BullMQ + worker. Redis зберігає стан черги, BullMQ керує завданнями, worker виконує роботу. Потрібно налаштувати збереження стану Redis, повтори з паузою, ліміти паралельності, моніторинг і захист від повторного проведення одного документа. Альтернатива — черга на PostgreSQL.

Важливо: після збою AI-запит інколи може повторитися. Тому результат і подальшу оплату/проведення документа треба захищати від дублювання. Черга не означає автоматичне збільшення лімітів AI-провайдера.

## 5. «Окреме API для документа» — що це насправді

Ти створюєш шаблон **Рахунок** з ідентифікатором **invoice** та інструкцією: «витягни номер, дату, валюту та суму».

| Адреса | Що робить зараз |
|---|---|
| POST /api/parse/invoice | Приймає будь-який рахунок і застосовує шаблон invoice |
| POST /api/parse/contract | Застосовує шаблон contract, якщо такий створено |
| POST /api/parse | Приймає файл і власний prompt |
| GET /api/documents/123 | Повертає збережений результат документа 123, без нового виклику AI |

**Сто рахунків → одна адреса шаблону → сто окремих ID результатів.** Новий сервер для кожного файлу не створюється. Слово invoice просто допомагає серверу знайти потрібну інструкцію в БД.

Наприклад, CRM відправила рахунок. Сервер знайшов інструкцію invoice, передав файл обраному AI, зберіг відповідь і повернув:

```json
{
  "id": 123,
  "originalName": "invoice.pdf",
  "typeSlug": "invoice",
  "extractedData": {"invoice_number": "INV-42", "currency": "EUR", "total": 250}
}
```

Це ілюстрація форми відповіді, а не реальна обробка. Зараз CRM чекає завершення запиту. З серверною чергою вона одразу отримуватиме jobId; пізніше перевірятиме статус або отримуватиме webhook. Такі асинхронні адреси ще не реалізовані.

Для компаній інтеграційний ключ повинен мати права лише на свою організацію. Зберігати потрібно його хеш, додати відкликання, ліміти запитів та журнал доступу. У поточній локальній версії такого API-захисту ще немає.

## 6. Як підключити AI зараз

Відкрий «Налаштування» → встав ключ потрібного провайдера → вкажи модель → «Зберегти» → «Перевірити» → вибери провайдера за замовчуванням → «Зберегти простір».

Перевірка отримує список моделей, але не надсилає документ і не перевіряє якість розпізнавання. Моделі можна змінювати: доступність залежить від акаунта. Автоматичного переходу на іншого провайдера немає.

Локальні ключі зашифровані; ключ шифрування зберігається на тому самому комп’ютері з обмеженими файловими правами. Це не захист від адміністратора комп’ютера. У виробничому середовищі використовуй серверні секрети; локальне редагування ключів вимкнене. Збережені у локальних налаштуваннях значення не переносяться автоматично на сервер.
